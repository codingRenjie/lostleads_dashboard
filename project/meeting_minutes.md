## 第一次会议：项目Kickoff启动会

**时间**：2025年10月9日（周四）14:00-16:30  
**地点**：经销商总部A会议室  
**出席**：老刘、富贵、季时雨、Bonnie总（全员）  
**记录**：富贵  
**会议类型**：项目启动

### 会议背景

Bonnie总作为销售总监，长期关注4S店战败客户的转化问题。在日常管理中，她发现销售顾问在企业微信工作群里反馈了大量战败客户的语音信息，但这些信息散落在聊天记录中，从未被系统性地收集和分析。Bonnie总希望借助数字化手段，将这些"沉睡的声音"转化为可行动的洞察，于是发起本项目并邀请老刘和富贵作为外部顾问提供端到端的解决方案支持。

### 会议内容

1. **Bonnie总阐述项目愿景**（30分钟）  
   - 目前4S店月均战败客户约**120组**，战败率高达**35%**，但战败原因缺乏系统分析
   - 销售顾问在企业微信群中每天产生约**30-50条**语音反馈，内容包含客户战败原因、竞品对比、价格异议等，这些信息非常有价值
   - 现有模式依赖销售主管人工翻阅聊天记录，效率低且容易遗漏
   - 期望目标是：**每天自动生成战败客户洞察报告**，帮助销售主管实时调整策略

2. **老刘分享行业洞察**（25分钟）  
   - 展示了同行业经销商的类似案例，语音数据驱动战败分析可将战败率降低**5-8个百分点**
   - 关键在于打通"语音采集 → 转写 → 结构化 → 洞察生成"的端到端链路
   - 建议引入成熟的ASR能力（如科大讯飞）和大模型分析能力（如KIMI K2.5）

3. **富贵介绍项目方法论**（20分钟）  
   - 采用**Design Thinking + Agile**混合模式，6周内完成从0到1的MVP验证
   - 项目分四个阶段：调研诊断（Week 1-2）→ 方案设计（Week 2-3）→ 开发验证（Week 3-5）→ 迭代交付（Week 5-6）
   - 每周至少1次同步会议，关键节点向Bonnie总汇报

4. **季时雨确认技术可行性**（20分钟）  
   - 企业微信支持群聊记录导出，语音文件格式为**silk**，需要转码处理
   - 门店有稳定的网络环境，可支持API调用
   - IT侧可配合提供测试环境和必要的服务器资源
   - 数据安全方面需确保客户隐私脱敏处理

5. **立项确认与下一步**（15分钟）  
   - 全员一致同意项目启动，代号定为**「老船长」**，寓意"引领航向、洞察风向"
   - 成立项目微信群，每日异步同步进展
   - 下次会议（10月13日）进行现状深度调研

- 项目排期表由老刘于10月10日前发出

## 第二次会议：现状调研与数据摸底

**时间**：2025年10月13日（周一）10:00-12:00  
**地点**：4S店销售部办公区（现场走访）  
**出席**：老刘、富贵、季时雨

**会议类型**：现状调研

### 会议内容

1. **销售部实地观察**（40分钟）  
   - 项目组在销售部办公区现场观察了销售顾问一天的工作流程
   - 发现销售顾问在接待客户后，习惯在企业微信"销售战败反馈群"中发送语音，内容多为"这个客户走了，觉得价格贵，去了隔壁店"、"客户贷款没批下来"等
   - 销售主管王经理每天下班前会花约**40分钟**翻阅群聊记录，手动摘录到Excel中

2. **数据采集分析**（30分钟）  
   - 季时雨协助导出了近**30天**的群聊数据，共计**1,247条**语音消息，平均每天约**42条**
   - 语音时长分布：5-15秒的短语音占**68%**，15-30秒占**25%**，30秒以上占**7%**
   - 语音内容初步分类：价格异议（**35%**）、竞品转移（**28%**）、金融方案不符（**18%**）、服务体验不满（**12%**）、其他（**7%**）

3. **利益相关者访谈**（30分钟）  
   - 与销售主管王经理、3名资深销售顾问进行了快速访谈
   - 王经理核心诉求：希望看到**每天的战败趋势变化**和**可执行的改进建议**，而不是原始数据
   - 销售顾问诉求：希望反馈能被"听到"，而不是石沉大海
   - 一致认为如果每天早会上能看到昨天的战败洞察，对当日客户跟进很有帮助

4. **技术环境摸底**（20分钟）  
   - 季时雨确认了门店现有的IT基础设施：
     - 企业微信为官方认证版本，支持机器人接口
     - 有一台闲置的Windows服务器可作为部署环境（8核16G）
     - 网络带宽上行50Mbps，足够支撑语音文件传输
   - 数据合规方面：Bonnie总已确认语音内容不涉及客户个人隐私信息，均为销售顾问的工作反馈

## 第三次会议：痛点分析与需求对焦

**时间**：2025年10月16日（周四）14:00-16:00  
**地点**：经销商总部B会议室  
**出席**：老刘、富贵、季时雨  
**记录**：富贵  
**会议类型**：需求分析

### 会议内容

1. **现状调研报告回顾**（20分钟）  
   - 富贵汇报了调研报告的核心发现
   - 当前战败分析流程存在**四大痛点**：
     - **采集缺失**：大量语音散落在聊天记录中，无系统采集
     - **处理低效**：主管人工翻阅+手动摘录，耗时且遗漏率高
     - **分析粗放**：仅做简单分类汇总，缺乏深度归因和趋势洞察
     - **行动滞后**：洞察产生周期长，错过最佳调整窗口

2. **用户旅程地图梳理**（35分钟）  
   - 项目组共同绘制了销售主管的"战败洞察用户旅程"：
     - **早晨8:30** 早会前 → 希望看到昨天的战败概览
     - **上午10:00** → 希望了解本周战败趋势变化
     - **下午15:00** → 希望针对具体战败案例调整跟进策略
     - **傍晚18:00** → 希望复盘当天战败情况
   - 明确了老船长需要覆盖的核心场景：**每日晨报**、**趋势周报**、**深度案例解析**

3. **需求优先级排序**（30分钟）  
   - 使用MoSCoW方法对需求进行优先级排序：
     - **Must Have**：每日自动采集语音 → ASR转写 → 提取战败信息 → 生成结构化表格 → KIMI大模型分析 → 输出洞察报告
     - **Should Have**：战败原因多维度下钻、竞品对比分析、销售顾问个人战败画像
     - **Could Have**：预测预警（识别高风险战败客户）、最佳话术推荐
     - **Won't Have**：CRM系统集成（二期考虑）、实时语音转写（成本过高）

4. **技术方案初步探讨**（25分钟）  
   - 老刘在白板上画出了初步的技术链路：
     ```
     企业微信群语音导出 → silk转码为MP3 → 科大讯飞ASR转文字 
     → 文本清洗与战败信息提取 → 结构化表格存储 
     → KIMI K2.5大模型分析 → 洞察报告生成 → 邮件/群推送
     ```
   - 季时雨确认各环节在技术上均可行，服务器资源足够支撑
   - 关于大模型调用方式，富贵建议采用**批量分析模式**（每天晚上汇总分析一次），而非实时流式分析，以控制成本

5. **下次会议预告**（10分钟）  
   - 10月21日进行方案设计评审，Bonnie总将出席
   - 老刘和富贵需在会前完成老船长的完整方案设计文档

## 第四次会议：「老船长」方案设计评审

**时间**：2025年10月21日（周二）14:00-17:00  
**地点**：经销商总部A会议室（大会议室）  
**出席**：老刘、富贵、季时雨、Bonnie总（全员）  
**记录**：季时雨  
**会议类型**：方案评审 / 里程碑汇报

### 会议内容

1. **老船长产品方案介绍**（45分钟）  
   - 富贵通过PPT向Bonnie总完整介绍了老船长的设计方案：
     - **产品定位**：面向4S店销售主管的"AI战败洞察助手"
     - **核心功能**：
       - **语音采集器**：每日自动导出企业微信群语音，转码后批量提交ASR
       - **信息提炼器**：从转写文本中提取战败客户信息（客户特征、战败原因、竞品信息、价格区间等），保存为结构化表格
       - **洞察引擎**：调用KIMI K2.5大模型分析结构化表格，生成战败趋势、归因分析、改进建议
       - **报告推送**：每日早8:00自动发送战败洞察报告（含摘要+详情链接）
     - **UI设计**：展示了报告看板的原型图，包含"每日战败概览"、"战败原因分布"、"竞品对比"、"趋势变化"四个模块

2. **技术架构评审**（30分钟）  
   - 老刘详细讲解了技术架构：
     - **前端**：Vue.js轻量级看板，适配PC和移动端
     - **后端**：Python FastAPI框架，负责调度ASR和大模型任务
     - **数据库**：SQLite（轻量，够用），存储结构化战败数据
     - **ASR服务**：科大讯飞语音转写API，支持批量提交
     - **大模型**：KIMI K2.5 API，通过Prompt Engineering生成洞察报告
     - **部署**：Docker容器化部署在门店服务器，每日定时任务自动运行
   - 季时雨确认架构合理，维护成本低，符合门店IT能力

3. **Demo演示**（20分钟）  
   - 老刘现场演示了一个**手工模拟的Demo**：
     - 用5条真实的语音数据，手动调用科大讯飞ASR转写，再调用KIMI K2.5分析
     - KIMI输出的洞察报告令人印象深刻，准确识别出"贷款审批速度慢"是本周主要战败原因，并建议"与金融专员建立快速审批通道"
   - Bonnie总对Demo效果表示高度认可

4. **Bonnie总反馈与决策**（30分钟）  
   - Bonnie总提出三个关键问题：
     - Q1：数据安全如何保障？答：所有数据处理均在门店本地服务器完成，语音文件不上传第三方，仅转写文本通过加密通道调用API
     - Q2：销售顾问需要改变工作习惯吗？答：完全不需要，销售顾问继续正常在群里发语音，后端自动采集
     - Q3：报告可以定制化吗？答：支持在管理后台配置报告模板和关注维度
   - **Bonnie总拍板**：方案通过，按此方案进入开发阶段，期望11月中旬完成MVP验证

5. **项目计划确认**（15分钟）  
   - 确认了修订后的项目里程碑：
     - Week 3（10.21-10.27）：技术架构搭建 + ASR接入
     - Week 4（10.28-11.3）：核心功能开发（采集+提炼+分析）
     - Week 5前半段（11.4-11.6）：集成测试 + Bug修复
     - Week 5后半段（11.7）：**MVP真实门店验证**（Bonnie总参加）
     - Week 6（11.10-11.20）：优化迭代 + 最终验收
