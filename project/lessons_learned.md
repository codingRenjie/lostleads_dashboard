## 一、项目成功因素

老船长项目最终取得24/25分的高验收评分，并获得了经销商总经理张总的认可，回顾来看，以下五个因素是项目成功的关键支柱。

### 1.1 正确的技术选型决策

项目在技术选型上坚持了"够用就好、务实为先"的原则，这一决策被事后证明是极为正确的。

前端选择了Vue.js而非React或Angular，原因很简单——季时雨对Vue更熟悉，后续运维他可以自主处理。后端选择FastAPI而非Django或Spring Boot，是因为项目本身是个轻量级流程编排服务，不需要复杂的ORM和中间件。数据库选择了SQLite而非MySQL或PostgreSQL，因为这个项目的数据量级很小（一家4S店每天几十条记录），SQLite完全够用，且免去了数据库安装配置的负担。

大模型的选择经历了短暂讨论。我们对比了KIMI K2.5、文心一言和通义千问。最终选择KIMI K2.5的核心原因是**中文长文本理解能力强**，且API文档清晰、调用稳定。实际运行中，KIMI在理解销售顾问口语化表达方面确实表现出色，比如"客户嫌贵跑了"能准确归类为"价格异议"，"隔壁店给了更低的价格"能提取出竞品信息和价格敏感信号。

> **经验**：技术选型不应追求最先进，而应追求**最匹配团队能力和业务场景**。

### 1.2 Sponsor的适度参与模式

Bonnie总作为项目Sponsor，她的参与模式堪称教科书级别。

她在Kickoff会议上清晰传递了业务愿景和成功标准（"每天自动生成战败洞察报告"），在方案设计评审会上拍板确认了方向，在MVP验证时以开放心态接受不完美并给出建设性反馈，在最终验收时给予团队充分认可。更重要的是，**她在项目执行阶段没有 micromanagement**——第二次到第三次会议期间她完全信任团队，没有要求参加每周的技术同步会。

这种"关键时刻在场、执行过程放手"的Sponsor参与模式，既确保了项目方向正确，又给了团队充分的空间去试错和创造。

> **经验**：Sponsor的最佳参与方式是**"定方向、给资源、关键时刻做决策"**，而不是全程盯进度。

### 1.3 早期真实数据验证

项目在第二次会议（10月13日）就进行了实地走访和数据摸底，这个决策节省了大量时间。

当我们导出30天的1,247条语音数据并进行初步分析时，发现了很多之前没想到的问题。比如，有7%的语音超过30秒，这些长语音往往是销售顾问在详细描述一个复杂的战败案例，信息密度很高，处理策略必须不同于短语音。再比如，我们发现"其他"分类占比7%，这说明现有分类体系不够完善，需要在方案设计阶段就考虑开放性分类。

如果我们没有尽早接触真实数据，而是在开发完成后才发现这些问题，返工成本将高得多。

> **经验**：AI项目的**第一周就应该接触真实数据**，哪怕是粗糙的摸底，也比闭门造车强。

### 1.4 小步快跑、快速验证

项目采用了一周一个迭代、每两周一个里程碑的节奏。MVP验证安排在第5周末（11月7日），距离Kickoff仅4周，这个节奏感非常好。

11月7日的MVP验证是整个项目的心理转折点。在那之前，团队心里都没底——不知道真实场景下的效果如何。当第一份实战报告生成、Bonnie总和王经理露出满意的表情时，整个团队的信心一下子上来了。这种**早期胜利（early win）**对于维持团队士气和获取干系人持续支持至关重要。

> **经验**：AI项目尤其需要**尽早制造"早期胜利"**，让团队和干系人看到希望。

### 1.5 团队能力互补

四人团队的能力组合非常理想。老刘有技术架构能力和AI项目经验，富贵有产品设计和前端能力，季时雨熟悉经销商内部环境和IT基础设施，Bonnie总懂业务且有决策权。这种"外部顾问+内部IT+业务Sponsor"的铁三角配置，确保了项目既有外部视野和专业能力，又有内部落地能力和业务权威。

> **经验**：AI落地项目最佳团队配置是**"外部专家+内部桥梁+业务Owner"**。

## 二、项目管理经验

### 2.1 混合项目管理方法

我们采用了**Design Thinking + Agile**的混合模式。项目前期（Week 1-2）用Design Thinking做调研和需求对焦，中期（Week 3-5）用Agile做开发迭代，后期（Week 6）用精益思想做优化。

这种模式非常适配AI项目的不确定性特征。AI项目的需求往往不是一开始就能完全明确的，需要通过数据探索和原型验证来逐步收敛。传统的瀑布模式（先写完整PRD再开发）不适合这种场景。

### 2.2 会议节奏设计

10次会议的分布经过了精心设计：
- **Week 1**：2次会议（密集调研）
- **Week 2**：1次会议（需求对焦）
- **Week 3**：1次会议（方案评审，Sponsor参加）
- **Week 4-5**：每周2次（开发冲刺，技术团队自组织）
- **Week 5末**：1次里程碑验证（Sponsor参加）
- **Week 6**：1次迭代同步 + 1次最终验收（Sponsor参加）

**关键经验**：Sponsor参加的会议只安排在关键决策点和里程碑验证点（第1、4、8、10次会议），而不是每周都参加。这样既能保证Sponsor的知情权，又不会浪费她的时间。

### 2.3 风险管理

项目中最主要的风险是**大模型效果不达预期**。为此我们做了三层风险缓释：

1. **技术层**：在第三次会议就用手工Demo验证了全链路可行性，确认KIMI的分析质量可接受后才进入开发
2. **设计层**：采用"规则引擎+大模型"的混合架构，即使大模型效果不理想，规则引擎也能兜底保证基础功能可用
3. **沟通层**：在方案评审时就没有过度承诺，明确告诉Bonnie准确率的提升需要数据积累和Prompt持续优化

实际运行中，大模型效果最终达到了96%的准确率，超出了最初承诺的90%。

### 2.4 范围管理

项目过程中出现了多次"需求诱惑"，团队需要坚决说"不"或"以后再说"：

- 第三次会议时，王经理提过"能不能顺便把成交客户的反馈也分析一下"——**决策**：聚焦战败客户，成交分析放到二期
- 第六次会议时，季时雨建议"要不要加上实时语音转写"——**决策**：批量模式已满足需求，实时模式成本高且不必要
- MVP验证时，Bonnie总提到"能不能集团化部署"——**决策**：先单店跑稳，集团化是二期目标

这种**有纪律的范围控制**是项目能在6周内高质量交付的关键。

## 三、技术与架构经验

### 3.1 技术架构：简洁是最高级的美

老船长的最终技术架构非常简单：

```
前端：Vue.js + ECharts + Tailwind CSS
后端：Python FastAPI + APScheduler（定时任务）
数据库：SQLite
ASR：科大讯飞语音转写API
大模型：KIMI K2.5 API
部署：Docker Compose + Nginx
```

没有消息队列，没有缓存层，没有微服务拆分。很多人会问：这会不会太简单了？

事实证明，对于一家4S店每天处理几十条语音的场景，这个架构不仅够用，而且有几个显著优势：
- **部署简单**：Docker Compose一键启动，季时雨30分钟完成部署
- **运维简单**：整个系统只有一个容器组，出问题容易定位
- **调试简单**：全链路日志在一个地方，排查问题效率高
- **成本低**：不需要额外采购Redis、MySQL等中间件许可

> **经验**：AI应用的技术架构应该从简单开始，**只有当性能瓶颈真实出现时，才考虑引入更复杂的组件**。

### 3.2 语音处理链路的关键细节

语音处理是整个系统的第一道关卡，有几个技术细节值得记录：

**silk转码**：企业微信语音原始格式是silk（Skype开发的编解码格式），需要使用`silk-v3-decoder`工具转码为WAV。我们踩过的坑是：部分silk文件的头部信息不完整，直接用工具会报错。解决方案是增加了一个预处理步骤，检测并修复不完整的silk头信息。

**语音时长过滤**：上线初期我们处理了所有语音，后来发现很多3秒以下的语音只是销售顾问的"收到"、"好的"之类无效内容。增加了一个>3秒的过滤条件后，ASR调用量减少了约15%，既省了成本又减少了噪音。

**批量提交策略**：科大讯飞ASR的批量提交接口有并发限制，超过10条同时提交会偶发超时。我们实现了分片提交+指数退避重试机制，将批次大小控制在8条以内，重试3次，超时率从约8%降到接近0。

### 3.3 Prompt Engineering的艺术

KIMI Prompt的设计和优化是整个项目中最具技术含量的环节之一。我们的Prompt经历了4个版本的迭代：

**V1（开发初期）**：简单的指令式Prompt，"请从以下文本中提取战败客户信息"，准确率约75%。

**V2（测试优化）**：增加了角色设定和输出格式要求，"你是一位汽车销售数据分析专家，请按以下JSON格式提取信息"，准确率提升到82%。

**V3（MVP前）**：引入了Few-shot Learning，在Prompt中给出了5个高质量示例，覆盖了各种口语化表达，准确率提升到91%。

**V4（迭代优化）**：增加到15个示例，并增加了"自检步骤"（"请先提取信息，然后检查是否有遗漏或不准确的地方，最后输出修正后的结果"），准确率提升到96%。

> **经验**：对于信息提取类任务，**Few-shot Learning比复杂的指令描述更有效**。示例的质量比数量更重要，15个覆盖各种场景的精选示例 > 100个雷同示例。

### 3.4 报告生成的工程化

洞察报告不是简单地把KIMI的输出直接推送，而是经过了一个工程化的处理流程：

1. **数据层**：KIMI输出JSON格式的分析结果
2. **模板层**：后端将JSON数据填充到预定义的HTML模板中
3. **渲染层**：使用Python的Jinja2模板引擎渲染，生成完整的HTML报告
4. **转换层**：通过WeasyPrint将HTML转换为PDF（可选）
5. **推送层**：企业微信机器人推送摘要+详情链接

这种"数据+模板+渲染"的分层设计，使得报告的样式调整不需要修改代码，只需修改HTML模板即可。富贵在迭代期间多次调整了报告的视觉设计，每次都是改模板文件然后重启服务，不需要动后端逻辑。

### 3.5 监控与告警

系统上线前，我们建立了一套简单的监控体系：

- **系统监控**：通过Prometheus + Grafana监控CPU、内存、磁盘使用率
- **业务监控**：每日记录语音处理数量、ASR成功率、KIMI调用耗时、报告生成状态
- **异常告警**：当ASR失败率>10%、KIMI调用超时>30秒、磁盘使用率>80%时，自动发送告警到企业微信群

这套监控体系在上线第一周就发现了一个问题：某天的定时任务没有触发。原因是系统时间从夏令时切换导致的cron表达式匹配异常。季时雨在2小时内定位并修复了这个问题，如果没有监控告警，可能要到第二天王经理反馈"今天没收到报告"时才会发现。

## 四、AI大模型应用经验

### 4.1 大模型不是万能的，关键在于找到合适的应用场景

老船长项目的成功，很大程度上是因为**选对了大模型的应用场景**。战败客户语音分析这个场景有几个天然适合大模型的特征：

1. **非结构化数据**：语音转写后的文本是非结构化的，传统规则很难处理口语化、方言化、省略化的表达
2. **理解而非创造**：任务重点是理解和提取信息，而不是创造新内容，这正好是大模型的强项
3. **容错可接受**：96%的准确率意味着每25条中只有1条可能有误，这种误差在业务上是可接受的
4. **有明确的标准答案**：战败原因分类是有明确业务定义的，KIMI的输出可以通过规则校验

我们在项目开始前就评估过，如果这个场景要求100%准确（比如财务对账），那就不适合用大模型。

> **经验**：评估一个场景是否适合大模型，可以看四个维度：**数据是否非结构化**、**任务是否偏理解**、**容错是否可接受**、**输出是否可校验**。

### 4.2 "人在环路"（Human-in-the-loop）的设计哲学

老船长系统虽然实现了全自动化，但在设计上保留了多处"人在环路"的机制：

- **人工校验入口**：在看板中提供了"编辑"功能，允许销售主管手动修正KIMI提取的信息
- **反馈闭环**：每条战败记录旁边有一个"👍/👎"按钮，主管可以对KIMI的分析质量打反馈
- **异常标注**：当KIMI的置信度低于阈值时，该条记录会被标记为"需人工确认"

这种设计有几个好处：
1. 系统上线初期准确率还不是100%时，用户不会觉得"AI胡来"
2. 用户的修正和反馈数据可以积累起来，用于后续Prompt优化
3. 建立了信任和透明度，用户知道"AI在帮我，但我也能控制"

上线两周内，王经理共进行了23次人工修正，这些修正数据成为我们优化V4版Prompt的重要参考。

### 4.3 大模型应用的成本控制

老船长项目的API调用成本控制做得比较好，主要有几个策略：

**批量模式而非实时模式**：每天晚上汇总当天的语音统一分析一次，而不是来一条分析一条。这样减少了API调用次数（合并请求比分散请求更省token）。

**分级处理策略**：
- 第一层：规则引擎做初筛（0成本），过滤掉明显无关的语音
- 第二层：轻量级Prompt提取基础信息（低成本）
- 第三层：深度分析只针对通过前两层的有效数据（高成本但数据量少）

**缓存机制**：对于重复出现的相似语音内容（比如"客户嫌贵走了"这种高频表达），结果会被缓存24小时，避免重复调用API。

实际运行中，每天的API调用成本约为**15-20元**，远低于业务价值。

### 4.4 大模型的幻觉问题与应对

在使用KIMI的过程中，我们遇到了几次"幻觉"问题：

- **案例1**：某条语音说的是"客户觉得配置不够"，KIMI却提取出了竞品名称（实际上并没有提到竞品）
- **案例2**：KIMI给某天的报告写了一篇很长的"趋势分析"，但数据只有一天，根本没有趋势可言

我们的应对策略：
1. **Prompt约束**：在Prompt中明确要求"只提取文本中明确提到的信息，不要推测"、"当数据不足以支撑趋势分析时，请如实说明"
2. **输出校验**：后端对KIMI的输出做规则校验，比如提取的竞品名称必须在预定义的竞争品牌列表中
3. **置信度评分**：让KIMI对自己的每条输出给出置信度评分，低置信度的内容标记为"待确认"

这些措施将幻觉问题的发生率从约8%降到了2%以下。

## 五、需求与业务对接经验

### 5.1 从"用户说"到"用户真正需要"

项目中最典型的一个需求转化案例是关于"报告内容"的。

王经理一开始提的需求是："能不能把每条语音的转写文字都列出来，我好一条一条看。"如果按这个需求做，报告会是一大堆原始文本，根本没法看。

经过深入访谈我们发现，王经理真正需要的不是"看原始文字"，而是"快速了解昨天发生了什么、问题在哪、该做什么"。这个真实需求通过"每日晨报"的形式来满足——一份一页A4纸的报告，包含关键指标、原因分布、趋势变化和行动建议。

王经理看到第一版报告后说："这比看一百条文字强多了。"

> **经验**：用户说的需求往往是**解决方案**（"给我原始文字"），而不是**问题本身**（"我想快速了解情况"）。产品经理的任务是挖掘背后的真实问题。

### 5.2 用户参与的最佳方式

项目中有两种用户参与方式，效果差异明显：

**方式A：王经理的深度参与**（效果好）
- 第二次会议就实地走访了他日常的工作流程
- 每次报告他都使用并给出具体反馈（"这个图表颜色不好区分"、"我希望看到环比"）
- 他的反馈直接转化为产品改进

**方式B：其他销售顾问的间接参与**（效果差）
- 只是通过王经理间接收集了他们的建议
- 建议比较笼统（"希望更好用"），难以转化为具体行动
- 最终验收时部分顾问表示"没听说过老船长"

**教训**：如果项目重来一次，我们会在第三次会议就邀请2-3名一线销售顾问参与需求对焦，而不仅仅依赖王经理作为中间人。这样能让更多一线用户有参与感，也能收集到更多元的需求视角。

### 5.3 数据驱动的需求优先级

我们在做需求优先级排序时，引入了一个简单但有效的指标：**影响人数 × 使用频率 × 痛苦程度**。

比如"战败客户挽回跟踪"功能的评分：
- 影响人数：3分（销售主管和2名经理）
- 使用频率：4分（每天使用）
- 痛苦程度：5分（之前完全靠记忆和Excel手动跟踪，非常痛苦）
- 总评分：60分（高优先级）

而"竞品话术推荐"功能的评分：
- 影响人数：5分（全体销售顾问）
- 使用频率：2分（偶尔使用）
- 痛苦程度：3分（主管有自己的话术手册）
- 总评分：30分（低优先级，放到二期）

这种量化的优先级评估方法，帮助团队在资源有限的情况下做出了更理性的取舍。

## 六、团队协作经验

### 6.1 远程+现场的混合协作模式

项目10次会议中，4次是远程会议（腾讯会议），6次是现场会议。远程会议主要用于开发阶段的技术同步（第5、6、9次会议），现场会议用于需要实地操作或Sponsor参加的会议（调研、方案评审、验收等）。

**远程会议的优势**：节省时间、高效同步信息  
**远程会议的劣势**：缺乏白板协作、难以进行复杂的讨论和决策  

我们的经验是：**技术同步可以远程，方案讨论和决策最好现场**。第七次会议（全天集成测试）如果远程做，效率至少降低50%，因为涉及到大量的现场联调和Bug修复。

### 6.2 异步沟通机制

除了定期会议，项目组还建立了异步沟通机制：

- **项目微信群**：每日21:00前同步当天进展，格式固定为"今日完成/明日计划/遇到障碍"
- **Git提交规范**：每次commit写明本次改动的目的，方便其他人快速了解进展
- **文档共享**：所有文档（会议纪要、技术方案、测试报告）都存放在共享文件夹，确保信息透明

这些机制减少了不必要的会议。如果没有异步沟通机制，第5和第6次会议之间的问题可能就需要再开一次会议来对齐。

### 6.3 冲突处理

项目进行到第六次会议时，老刘和富贵在技术方案上产生了分歧。老刘认为应该先优化后端性能再增加新功能，富贵认为应该先完善前端用户体验。

最终解决方式是：**各自列出不做对方方案的代价**，然后一起评估。老刘承认前端体验差会影响用户验收，富贵承认后端性能瓶颈会导致系统不稳定。最后双方各让一步——先花2天做关键性能优化（足以支撑验收），然后同步进行前端优化。

> **经验**：技术分歧不要演变成"谁对谁错"，而应该转化为**"不同选择的机会成本分析"**。

### 6.4 外部顾问与内部团队的融合

老刘和富贵作为外部顾问，与季时雨（内部IT）的协作是项目成功的关键。

做得好的地方：
- 从第一天就把季时雨当作**项目核心成员**而非"提供资源的接口人"，所有技术决策都征求他的意见
- 老刘在第七次会议（集成测试）时主动到经销商IT机房现场，和季时雨面对面一起调试，建立了深厚的战友情
- 代码和文档全部交给季时雨管理，确保项目结束后他可以独立运维

可以改进的地方：
- 项目初期老刘和富贵对经销商内部的审批流程不够了解，导致科大讯飞ASR账号申请花了比预期更长的时间。如果前期就让季时雨深度参与技术选型决策，这个问题可以避免。

## 七、踩过的坑

### 7.1 坑一：silk转码的兼容性问题（第5次会议暴露）

**问题描述**：企业微信语音导出后，约5%的silk文件转码失败，报错"invalid silk header"。  
**根本原因**：这些语音是在网络不佳的环境下录制的，silk编码时头部信息写入不完整。  
**解决方案**：增加了一个silk文件预处理模块，检测并修复不完整的头部信息。  
**影响**：延迟了半天开发进度。  
**教训**：处理企业微信语音时，**一定要做好异常文件的兼容处理**，不要假设所有文件都是规范的。

### 7.2 坑二：科大讯飞ASR的批量提交超时（第6次会议暴露）

**问题描述**：当一次提交的语音超过10条时，ASR接口偶发超时（约8%的概率）。  
**根本原因**：科大讯飞批量接口的并发处理有上限，超过阈值后请求会被排队，排队时间过长导致客户端超时。  
**解决方案**：将批次大小从20条减到8条，增加指数退避重试机制（第一次1秒后重试，第二次2秒，第三次4秒）。  
**影响**：处理200条语音的时间从8分钟增加到12分钟，但成功率提升到99.5%。  
**教训**：调用第三方API时，**永远假设它会超时或失败**，做好重试和降级策略。

### 7.3 坑三：KIMI Prompt的过度优化（第7次会议暴露）

**问题描述**：V3版Prompt为了追求高准确率，写得过于复杂，包含了大量约束条件，结果导致KIMI在某些简单场景下"想太多"，输出不必要的分析内容。  
**根本原因**：Prompt不是越长越好，过多的约束会让模型困惑。  
**解决方案**：V4版Prompt采用了"分层指令"结构——先给总体目标，再给具体步骤，最后给示例。去掉冗余的约束，保留核心的指引。  
**影响**：Prompt从约2000字精简到约1200字，准确率反而从91%提升到96%。  
**教训**：**Prompt设计要遵循"奥卡姆剃刀"原则**——在达到目标的前提下，越简洁越好。

### 7.4 坑四：移动端看板适配（第6次会议暴露）

**问题描述**：前端看板在PC端显示正常，但在部分安卓手机的微信内置浏览器中，ECharts图表显示异常（坐标轴错位、Tooltip不弹出）。  
**根本原因**：微信内置浏览器（X5内核）对某些CSS属性和JavaScript API的支持不完整。  
**解决方案**：引入polyfill兼容层，同时提供了降级方案——在移动端用预渲染的静态图表图片替代交互式ECharts。  
**影响**：增加了约1天的开发工作量。  
**教训**：**项目第一周就应该在目标用户的真实设备上做兼容性测试**，而不是只在开发者的Chrome浏览器上测。

### 7.5 坑五：夏令时切换导致定时任务失效（上线第一周暴露）

**问题描述**：系统上线后的某天，定时任务没有触发，当天的报告没有生成。  
**根本原因**：11月的第一个周日，系统从夏令时切换回标准时间，cron表达式中的时间匹配出现了偏差。  
**解决方案**：将定时任务从cron表达式改为固定间隔模式（每24小时运行一次），同时使用系统的UTC时间而非本地时间做调度。  
**影响**：当天报告延迟了2小时生成，幸好有监控告警及时发现。  
**教训**：**任何依赖时间的系统都要考虑时区切换问题**，特别是在夏令时/冬令时交替的季节上线。

### 7.6 坑六：没有早期让一线销售顾问参与（复盘时发现）

**问题描述**：项目验收时，部分一线销售顾问表示"没听说过老船长"，虽然王经理在用，但顾问们的参与感不强。  
**根本原因**：项目组主要通过王经理间接收集需求，缺少与销售顾问的直接对话。  
**影响**：部分潜在需求没有被挖掘出来（比如"希望看到具体客户的跟进建议"这个需求到第九次会议才正式提出）。  
**教训**：**AI项目的最终用户不应该是"被通知"的，而应该是"被邀请参与"的**。

## 八、可复用的方法论

### 8.1 「语音数据→洞察」的通用Pipeline

老船长项目沉淀了一个通用的"语音数据→结构化信息→洞察报告"处理Pipeline，可以在其他类似场景中复用：

```
语音采集 → 格式转码 → ASR转写 → 文本清洗 → 信息提取（大模型+规则） 
→ 结构化存储 → 数据分析（大模型） → 报告生成 → 推送触达
```

这个Pipeline适用于任何"散落在聊天记录中的语音/文本反馈需要被系统化分析"的场景，比如：
- 客服中心的通话录音分析
- 门店顾客的口头反馈汇总
- 销售团队的日常汇报分析
- 售后维修的问题归类

### 8.2 AI项目的「四步验证法」

我们在项目中总结了一个AI项目的验证方法，命名为**「四步验证法」**：

1. **手工验证**（第3次会议）：用少量真实数据，手工调用API验证效果是否可接受
2. **链路验证**（第7次会议）：全链路自动化跑通，用批量数据验证稳定性
3. **真实验证**（第8次会议）：在真实业务环境中运行，让真实用户反馈
4. **规模验证**（二期目标）：在多场景/多用户/长时间运行下验证可靠性

只有在每一步验证通过后才进入下一步，这样可以及早发现问题，避免后期返工。

### 8.3 Prompt优化的「示例驱动法」

我们在KIMI Prompt优化中总结了一个有效的方法论：

1. **收集困难案例**：找出模型处理不好的典型输入（口语化、歧义、省略等）
2. **编写黄金标准答案**：人工写出这些案例的理想输出
3. **植入Prompt**：将这些输入-输出对作为Few-shot示例放入Prompt
4. **迭代测试**：用测试集验证效果，重复步骤1-3直到满足目标

这个方法的核心理念是：**与其在Prompt中写一堆规则，不如给模型看几个好例子**。

### 8.4 「业务+技术+AI」三角协作模型

老船长项目验证了以下协作模型的有效性：

- **业务方（Bonnie总/王经理）**：定义"做什么"和"为什么"，验收"好不好用"
- **技术方（老刘/富贵）**：定义"怎么做"和"用什么技术"，保证"做得出来"
- **AI方（KIMI/科大讯飞）**：承担"理解非结构化数据"和"生成洞察"的任务
- **桥梁方（季时雨）**：连接以上三方，保证"在真实环境中跑得通"

这个模型的关键是：**三方不是串联关系（业务提需求→技术实现→AI赋能），而是并联协作关系**，从第一天就坐在一起讨论。

## 九、给未来项目的建议

### 9.1 给业务Sponsor的建议

1. **项目启动前先想清楚"成功标准"**：Bonnie总在Kickoff会上说"每天自动生成战败洞察报告"，这个清晰的成功标准帮助团队始终聚焦。
2. **给团队信任和空间**：Bonnie总没有每周追问进度，而是在关键节点参与，这种信任让团队敢于试错。
3. **让一线用户深度参与**：如果能让更多销售顾问从需求阶段就参与进来，最终产品的用户接受度会更高。

### 9.2 给技术负责人的建议

1. **架构从简，演进逐步**：不要一上来就设计复杂的微服务架构，先让系统跑起来，再按需演进。
2. **Prompt Engineering需要迭代思维**：不要期望第一版Prompt就完美，准备好花30%的时间在Prompt调优上。
3. **监控是上线前必须完成的，不是上线后才补充的**：如果没有监控告警，很多问题发现时已经造成了业务影响。
4. **永远准备好Plan B**：大模型效果不达预期时，规则引擎可以兜底；API服务故障时，本地缓存可以支撑。

### 9.3 给产品经理的建议

1. **第一周就接触真实数据**：不要等产品设计完才开始看数据，数据会告诉你很多设计文档不会告诉你的事情。
2. **区分"用户说的"和"用户真正需要的"**：用户经常提出解决方案而非问题，挖掘背后的真实需求是关键。
3. **早期制造胜利**：在项目进行到30-40%时就争取做一个可演示的原型或MVP，让团队和干系人看到进展。
4. **功能做减法不做加法**：资源有限时，宁愿把一个功能做到极致，也不要做十个功能每个都平庸。

### 9.4 给AI项目团队的建议

1. **选对场景比选对模型更重要**：再强大的模型，用在不合适的场景上也是浪费。
2. **大模型是助手不是替代者**：设计系统时要保留人工干预的入口，建立"人在环路"的信任机制。
3. **做好数据积累**：用户的每一次修正、每一个反馈都是优化模型的宝贵数据，要建立反馈闭环。
4. **成本控制要从设计阶段开始考虑**：批量处理、分层处理、缓存机制等策略应该在架构设计时就纳入考量。

## 十、团队成员个人反思

### 老刘（外部技术顾问）

> 老船长是我参与的第三个AI落地项目，也是交付最顺利的一个。回头看，我认为最关键的是我们在项目第一周就做了"可行性验证"——用真实数据手工跑通了全链路。很多AI项目失败的原因是团队在不确定技术可行性的情况下就开始大规模开发，最后发现模型效果不达标，前面投入的工程开发全部白费。
>
> 另一个深刻体会是Prompt Engineering的重要性被严重低估了。在这个项目中，我们花了将近四分之一的时间在Prompt设计和优化上，这个投入是值得的。V1到V4的Prompt迭代让准确率从75%提升到96%，这比换任何一个更强大的模型都有效。
>
> 如果说有什么遗憾，那就是我们应该更早地考虑多门店部署的扩展性。现在老船长的代码是为单店设计的，如果二期要做集团化部署，部分模块需要重构。如果当初花多一两天做适度的抽象，现在会轻松很多。

### 富贵（外部产品顾问）

> 作为产品设计负责人，我最大的感悟是：AI产品的设计逻辑和传统软件完全不同。传统软件是"用户输入→系统处理→确定性的输出"，而AI产品是"用户输入→系统理解→概率性的输出"。这个本质区别要求我们在设计上做很多调整。
>
> 比如，传统软件的表格是"展示数据"，而AI产品的表格是"展示AI的理解"——用户看到的每一条数据背后都经过了模型的解读。这意味着我们必须提供"为什么这样理解"的解释能力，以及"如果理解错了你可以纠正"的编辑能力。在老船长中，我们加入了置信度标记和人工编辑功能，这些在传统软件中是不必要的，但在AI产品中是必不可少的。
>
> 另一个感悟是关于用户采纳的。王经理之所以 quickly 接受了老船长，不是因为技术多先进，而是因为它解决了他每天花40分钟翻聊天记录的痛苦。AI产品的价值不在于"用了AI"，而在于"解决了问题"。
>
> 遗憾之处在于移动端适配开始得太晚。我们直到第六次会议才发现微信内置浏览器的兼容性问题，那时候大部分前端开发已经完成，返工成本较高。如果项目重来，我会在第三周就开始在目标设备上做兼容性测试。

### 季时雨（经销商IT）

> 这是我第一次深度参与AI项目。在此之前，我对AI的理解停留在"聊天机器人"的层面。通过这次项目，我真正理解了AI在实际业务场景中的落地方法。
>

> 如果说有什么可以反思的，我应该更早地让一线销售顾问参与进来。项目验收时有些顾问表示没听说过老船长，这说明他们的参与感不够强。如果能让更多一线声音进入需求阶段，产品可能会更贴合实际使用场景。
>
> 另一个思考是关于组织层面的。老船长的成功证明了一个模式：业务痛点 + AI技术 + 敏捷执行 = 快速价值。接下来我需要思考的是，如何在经销商内部建立这种能力，而不只是依赖外部顾问。季时雨的成长让我很欣慰，我希望未来能有更多这样的内部AI落地能力。
